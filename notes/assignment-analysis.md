# Анализ задания

## 1. Что создается

Два интерфейса для представления иерархической организационной структуры: в виде древа и в виде таблицы.
Оба интерфейса должны быть интерактивны и удобны для изучения информации.

## 2. Явные требования

### Step Foundation

— базовый сетап проекта Vite, React, TS, абсолютные импорты
— мок-сервер с GET-запросом, но в дальнейшем потребуется реализация live-пачтей (ws, sse или polling)
— клиентская валидация данных, обработчик ошибок
— работа с плоским массивом данных. вывод: на клиенте должно быть превращение плоского массива в иерархическую структуру
— кэширование , инвалидация только при фактическом изменении данных (обязательны кэш и семантика свежести данных, а механизм хранения оставить решением). stale time — 5с.
— предотвращение излишних запросов
— разделение слоя запросов, логики, UI
— UI с интерактивным деревом отображения (раскрытие/скрытие ветвей, второй (от корня) уровень открыт по умолчанию)
— В узле дерева нужно показывать имя узла (тип указывать не стоит, так как это будет понятно по расположению узла в иерархии), количество сотрудников (headcount) и цветовой индикатор производительности, основанный на шкале 0-100 (это ux-решение, а не факт. Сначала нужно определить семантику столбца "Уровень")
— изоляция логики обновления и кэширования данных от view
— желательно использовать styled-components
— inline css запрещен
— UI-библиотеки не нужны
— обработчики и индикаторы состояния запроса и fallback
— детерменированные данные: минимум 40 узлов и 3 уровня вложенности

### Step Core

— второй контейнер с UI-представлением данных в виде таблицы
— выбор между "переключением между режимами Дерево и Таблица" и "адаптивным разделением окна при ширине больше 1280 px"
— корректная работа синхронного обновления данных в обоих представлениях
— синхронизация выбора (selection) на элементе между таблицей и деревом (по крайней мере, в одну сторону: строка -> узел дерева)
— сортировка по всем столбцам (первое нажатие — переход в состояние прямой сортировки, второе — переход в состояние обратной сортировки, третье — дефолтное значение. уточнить, сколько лучше состояний (2: прямая и обратная сортировка или 3: прямая, обратная и отсутствие) для UX)
— поиск по имени (debounce 250мс)
— агрегация (есть вопросы по значению, не по реализации)
— однократная агрегация и кэширование (в тз указана мемоизация, подумаю)

### Доработка

— websocket, sse или polling (принимаю решение на основе количества, частоты изменений) для обмена данных с сервером realtime
— запрет на структурные патчи, только скалярные данные! (name, headcount, budget, performance)
— обновление ячеек с fade-out
— пересчет значений только измененного узла и его предков
— навигация по таблице с помощью Enter, стрелочек и Home/end
— анимация раскрытия дерева через prefers-reduced-motion
— экспоненциальный бэкофф при разрыве соединения

### Бонус

— docker (compose up) для поднятия клиента и сервера
— прикрутить nginx: прокси, статика фронтенда
— прод сборка < 200кб
— AI-поиск (по api? )

## 3. Нефункциональные требования

— доступность: понятная индикация текущего процесса получения, обновления, обработки данных и взаимодействия с интерфейсом (в том числе в UI-компонентах)
— производительность: использование кэширования, прод-сборка <200 кб, остальные параметры неизвестны

## Decisions

### Realtime patch scope

**Decision:** During realtime operation, organization topology and node
identity are immutable.

A realtime patch may update any subset of:

- `headcount`;
- `budget`;
- `performance`;

for an existing node.

The following are outside realtime scope:

- `name` changes;
- `parentId` changes;
- node insertion;
- node deletion.

**Rationale:** This is the minimum model that satisfies the assignment's
realtime requirements while preserving the required update path of
recalculating only the affected node and its ancestors.

**Consequences:**

- hierarchy indexes can remain stable during realtime operation;
- a patch affects exactly one node's raw metrics;
- aggregate recomputation only needs the node and its ancestor chain;
- realtime does not need to handle reparenting or structural mutations;
- recovery does not need to reconcile topology changes.
