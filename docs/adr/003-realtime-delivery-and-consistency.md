# ADR 003: Realtime-транспорт и согласованность данных

- Статус: принято
- Дата: 2026-09-15

## Контекст

На этапе 3 сервер должен доставлять клиенту изменения метрик существующих
узлов без полного refetch. Поток однонаправленный: сервер меняет только
headcount, budgetиperformance, а клиент не отправляет через realtime-
соединение команды или структурные изменения организации.

Транспорт должен поддерживать явный lifecycle соединения, индикацию состояния,
переподключение с backoff и освобождение ресурсов. Протокол также должен
защищать query-owned OrgSnapshot от повторной обработки событий, пропусков в
потоке и гонки, при которой завершившийся позднее GET содержит более старые
метрики, чем уже принятый realtime-патч.

## Рассмотренные варианты

### WebSocket

Плюсы:

- двунаправленный канал и возможность в дальнейшем добавить клиентские команды;
- полный контроль над прикладным протоколом и heartbeat.

Минусы:

- двунаправленность не требуется для metric-only server-to-client потока;
- нужны отдельные protocol framing, reconnect и resume-механизмы;
- решение добавляет сложность, не оправданную требованиями mock dashboard.

### Server-Sent Events

Плюсы:

- соответствует однонаправленной доставке событий поверх обычного HTTP;
- браузер предоставляет EventSource, а формат поддерживает идентификаторы
  событий и возобновление потока;
- поток естественно проходит через существующий API proxy и не требует нового
  production-протокола.

Минусы:

- канал не подходит для двунаправленного обмена;
- контролируемый restart и gap recovery всё равно требуют прикладной логики;
- сервер должен явно управлять heartbeat, bounded history и медленными или
  отключившимися клиентами.

### Эффективный polling

Плюсы:

- использует обычные короткие HTTP-запросы;
- не требует долгоживущего соединения и stream lifecycle.

Минусы:

- создаёт запросы даже при отсутствии изменений;
- частота polling вынуждает выбирать между задержкой обновлений и лишней
  нагрузкой;
- сложнее выполнить требование немедленного patch-применения без превращения
  GET в постоянный механизм инвалидации.

## Решение

Использовать SSE endpoint /api/org-tree/events и браузерный EventSource для
однонаправленного потока metric-only патчей. Соединение создаётся только после
появления валидного snapshot, принадлежит dashboard resource и закрывается при
уходе его последнего потребителя.

Каждое прикладное событие содержит:

json
{
"type": "metric.patch",
"eventId": "evt-42",
"sequence": 42,
"nodeId": "node-7",
"metrics": {
"headcount": 12,
"budget": 1000,
"performance": 84
},
"updatedAt": "2026-09-15T12:00:00.000Z"
}

metrics содержит только реально переданные поля из разрешённого набора.
Клиент валидирует envelope и отклоняет malformed, structural и unknown-node
патчи до изменения кэша.

Сервер присваивает событиям уникальный eventId и глобальный монотонный
sequence, хранит ограниченную историю последних событий и replay-ит доступный
хвост после Last-Event-ID. Для управляемого restart клиент также может передать
последний event id query-параметром, поскольку конструктор EventSource не
позволяет задать произвольный request header.

Первое событие после загрузки страницы устанавливает исходную позицию потока.
После неё клиент принимает только следующий contiguous sequence, игнорирует
дубликаты и старые события. При обнаружении gap он приостанавливает применение
патчей, выполняет полный GET как baseline recovery и перезапускает SSE с
последнего успешно применённого event id, чтобы bounded-history replay доставил
пропущенные события. Сам recovery GET не заменяет replay: mock server не
персистит сгенерированные metric patches.

Принятый contiguous патч применяется иммутабельно непосредственно к TanStack
Query cache согласно ADR 001 и ADR 002. Он не инвалидирует query и не вызывает
полный GET только из-за факта поступления патча. updatedAt каждого узла служит
watermark при reconciliation: более старое значение из позднего GET не должно
затереть более новый realtime-результат; при сохранении realtime-узлов агрегаты
нового snapshot рассчитываются из согласованного набора raw-метрик.

После разрыва соединение переподключается с детерминированным capped exponential
backoff 1, 2, 4, 8, 16, 30, 30... секунд. Успешное открытие сбрасывает backoff.
Сервер отправляет heartbeat, клиент считает долго молчащее соединение
неактивным и перезапускает его. Детерминированная политика выбрана вместо jitter,
потому что scope ограничен mock server и единичным клиентом, а воспроизводимые
fake-timer проверки важнее распределения массовых reconnect.

## Последствия

- realtime-канал остаётся однонаправленным; будущие client-to-server команды
  потребуют отдельного HTTP API или пересмотра транспорта;
- сервер обязан поддерживать корректные SSE headers, heartbeat, cleanup
  отключённых клиентов и ограниченную replay history;
- bounded history означает, что восстановление не гарантируется одним replay,
  если нужные события уже вытеснены; полный GET остаётся baseline recovery;
- eventId, sequence и updatedAt являются частью consistency-протокола, а не
  только транспортными метаданными;
- query cache остаётся единственным владельцем опубликованного snapshot, а
  realtime layer выполняет валидированный атомарный переход его состояния;
- дерево и таблица наблюдают один и тот же результат патча без отдельной
  синхронизации и без patch-triggered refetch;
- смена SSE на WebSocket или polling потребует сохранить envelope, ordering,
  recovery и cache-reconciliation semantics либо принять новый ADR.
