# ADR 001: Клиентское представление организационных данных

- Статус: принято
- Дата: 2026-09-15

## Контекст

API возвращает плоский массив узлов организации. Клиенту нужны быстрый поиск
узла по id, обход иерархии в обе стороны, расчёт агрегатов, независимые
проекции дерева и таблицы, общая выборка узла и применение realtime-патчей к
метрикам существующих узлов.

Во время realtime-обновлений топология неизменна. Патч может менять только
headcount, budget и performance. После патча агрегаты пересчитываются
только для изменённого узла и его предков.

## Рассмотренные варианты

### Вложенное дерево как основное представление

Плюсы:

- естественный рекурсивный рендеринг дерева;
- простой обход потомков и первоначальный post-order расчёт агрегатов.

Минусы:

- поиск по id и подъём к родителям требуют обходов или дополнительных
  индексов;
- для таблицы нужна отдельная плоская проекция;
- иммутабельный патч заменяет узел и всю цепочку объектов до корня;
- дополнительные индексы легко превращаются во второе, рассинхронизируемое
  представление данных.

### Плоский массив как основное представление

Плюсы:

- совпадает с формой ответа API;
- удобен для перебора, фильтрации и сортировки таблицы;
- имеет минимальную начальную сложность.

Минусы:

- поиск узла, родителя и детей требует повторных линейных обходов;
- наивный обход дерева и агрегация могут стать квадратичными;
- эффективная реализация всё равно потребует индексов по id и parentId;
- легко случайно изменить исходный порядок через сортировку массива.

### Нормализованные сущности со множеством равноправных хранимых моделей

Плюсы:

- быстрые адресные операции и обходы;
- можно отдельно оптимизировать дерево, таблицу и realtime-обновления.

Минусы:

- хранение самостоятельных копий вложенного дерева, строк таблицы и сущностей
  создаёт несколько источников истины;
- каждое обновление требует синхронизации всех моделей;
- сложность несоразмерна объёму и требованиям задания.

### Дисциплинированное нормализованное хранилище

Плюсы:

- одна каноническая запись каждого узла, адресуемая по id;
- прямой доступ к родителю через parentId и к детям через стабильный индекс;
- первоначальная агрегация выполняется за O(n), а после патча пересчитывается
  только изменённый узел и цепочка его предков;
- дерево и таблица используют одни данные и не могут расходиться как
  независимые копии;
- неизменная realtime-топология позволяет построить иерархические индексы один
  раз для принятого снимка данных.

Минусы:

- требуется отдельный шаг нормализации и проверка инвариантов иерархии;
- материализованные агрегаты должны обновляться согласованно с raw-метриками;
- рендеринг дерева выполняет обращения к индексам вместо прямого доступа к
  node.children.

## Решение

Использовать дисциплинированную форму нормализованного хранилища:

- nodesById — единственный канонический источник серверных данных узлов;
- rootIds, childrenByParentId и при необходимости depthById — стабильные
  производные индексы топологии;
- aggregatesById — материализованные производные агрегаты: суммарные
  headcount, budget и взвешенная сумма performance * headcount;
- средняя эффективность вычисляется из взвешенной суммы и суммарного
  headcount, а не хранится как независимый источник истины;
- дерево, отфильтрованные и отсортированные строки таблицы и форматированные
  значения являются производными проекциями и не хранят собственные копии
  узлов;
- общий выбор между деревом и таблицей хранится как selectedNodeId, а не как
  ссылка на объект или индекс строки.

Вариант выбран как минимальная архитектура, которая одинаково подходит для
всех обязательных этапов. Foundation получает прямые индексы для построения
дерева, Core — однократно рассчитанные агрегаты и независимые табличные
проекции, Polish — адресное обновление raw-метрик и только одной цепочки
агрегатов. При этом решение не требует отдельного глобального стора,
универсального graph layer или нескольких синхронизируемых моделей.

## Метод агрегации

### Первоначальный расчёт

После валидации данных и построения иерархических индексов агрегаты считаются
одним post-order обходом: сначала для детей, затем для родителя. Для каждого
узла материализуются:

text
totalHeadcount = node.headcount + sum(child.totalHeadcount)
totalBudget = node.budget + sum(child.totalBudget)
weightedPerformanceSum =
node.performance * node.headcount

- sum(child.weightedPerformanceSum)

Средняя эффективность не является самостоятельным хранимым значением и
вычисляется как:

text
weightedPerformanceSum / totalHeadcount

При нулевом totalHeadcount числовое среднее отсутствует и отображается в UI
как —. Первоначальный расчёт имеет сложность O(n): каждый узел и каждое
отношение родитель–ребёнок обрабатываются один раз.

### Пересчёт после realtime-патча

После изменения raw-метрик существующего узла его агрегат заново вычисляется
из собственных актуальных метрик и актуальных агрегатов непосредственных
детей. Затем тем же способом снизу вверх пересчитывается каждый предок до
корня. Узлы вне этой цепочки не пересчитываются.

Сложность такого обновления равна суммарному числу непосредственных детей у
пересчитанных узлов. В худшем случае она может достигать O(n), а не строго
O(h). Для набора чуть больше 40 узлов это несущественно и точнее отражает
выбранный алгоритм.

Рассматривалась дельта-пропагация, при которой разница между старым и новым
вкладом прибавляется к агрегатам всех предков. Она могла бы обеспечить O(h),
но усложняет одновременное изменение headcount и performance, повторную
обработку патчей и защиту от накопления ошибок. Пересчёт из текущих raw-данных
и агрегатов детей выбран как более простой, идемпотентный и объяснимый вариант,
который прямо соблюдает требование пересчитывать только изменённый узел и его
предков.

## Последствия

- parentId и childrenByParentId должны описывать одну и ту же ациклическую
  иерархию;
- каждый узел должен принадлежать ровно одному корню;
- realtime-патч должен ссылаться на существующий узел и не менять топологию;
- raw-метрики и затронутые агрегаты должны обновляться как одно логически
  согласованное изменение;
- агрегат каждого пересчитанного узла должен равняться его raw-вкладу плюс
  актуальные агрегаты непосредственных детей;
- средняя эффективность всегда выводится из weightedPerformanceSum и
  totalHeadcount, поэтому не может рассинхронизироваться с ними;
- агрегаты узлов вне цепочки предков изменённого узла должны оставаться без
  изменений;
- сортировка и фильтрация не должны изменять канонические данные или порядок
  детей;
- выбор конкретных структур Map/Record, владельца состояния, cache layer и
  realtime transport остаётся отдельным решением.
